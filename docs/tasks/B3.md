# B3: A launch that fails the launch filters never reaches the watched set

Mode: B · Writer: subagent (sonnet) · Depends on: B1, B2 (`filters.ts`, `filter.sampled`) · PLAN row: B3

## Current behavior
Observed: the Scout promotes on `caller_buy`, `smart_buy`, `heat` or `metrics` (`services/core/src/senses/scout.ts:169`) with no launch check. Blocklists exist only in the Risk Gate (`services/core/src/mind/risk.ts:99-101`), so a blocked creator's coin is still watched, stored and backfilled.

## Required behavior
Before `coin.watched` (`scout.ts:179`), the launch features (dev buy SOL, block-0 sniper share, bundle share) are checked against `config/filters.json` `launch`, and creator, mint and trigger wallet against the owner lists (`blocked_creators`, `blocked_mints`, `blocked_wallets`, as of now). A refused launch is counted per reason and sampled as `filter.sampled`. Its trades still fold into the Index rollups.

## Which source feeds the door (decided by measurement 2026-10-19)
`docs/research/nats-vs-rpc-latency.md`: NATS is as fast as any RPC push stream (only quicknode led, by about 50 ms) and sees about 2.7 times more trades, because `logsSubscribe` shows only transactions that name the pump program. So the door stays on NATS (the Scout already reads it), and chain data is the second look, not a second door:
1. Door (this task): NATS trades and launches, features from `slot_index_id` as now.
2. After promotion: Backfill reads the coin's first trades from RPC (`backfill.ts:132`), which gives what NATS lacks (order inside a slot, the signer). A promoted coin whose chain features disagree with the NATS ones writes `system.source_disagree` (RPC wins, per `docs/PIPELINE.md` section 2) and re-runs the check; if it now fails, the coin leaves the watched set with `system.gap`-style note. This is the only RPC work B3 adds; it costs nothing for the launches that never promote.
Not in B3: a second live stream from RPC (needs Anchor event decoding and still misses pump-swap trades).

## Invariants
The deny list is the owner's existing `blocked_wallets` and `blocked_creators` (known bad deployers and traders); the door checks both the creator and the trigger wallet. The list is loaded only by `ctl lists load`; no code adds to it (owner decision 2026-10-19).
The Risk Gate keeps its own blocklist check: the door adds a wall, it does not replace one. The filter uses only features known at the trigger trade (no lookahead).
