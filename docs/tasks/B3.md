## Where each fact comes from, and what happens when a source fails
NATS is the door (`docs/research/nats-vs-rpc-latency.md`: as fast as any RPC push stream, about 2.7 times the coverage). The RPC pool supplies what NATS does not carry. The pump.fun HTTP API is rate limited, so it is never the only source for anything. Each fact has an ordered list; the first source that answers wins and the one used is recorded.

| Fact | 1st | 2nd | 3rd | If none answers |
|---|---|---|---|---|
| Creator, curve account, launch time | NATS `newCoinCreated.prod` (feed server) | RPC pool: the creation transaction (`getSignaturesForAddress` on the curve account, oldest, then `getTransaction`) | pump.fun HTTP coin lookup | `from_birth: false`, creator unknown |
| Dev buy SOL | NATS trades: the first buy whose `userAddress` equals `creatorAddress` | RPC pool: the creation transaction | none | unknown |
| Block-0 snipers and bundle share | NATS `slot_index_id` (same slot as the first trade) | RPC pool: the first transactions of the coin, which also give order inside the slot and the signer (Backfill's reader, `backfill.ts:132`) | none | unknown; `from_birth` false means bundle features are not measured, as today |
| Trigger wallet and mint lists | owner lists as of now | | | |

- A fact is read from a lower row only when the one above has not answered: the coin joined mid-life (no launch message), or the fact needs more than NATS carries. RPC calls go through `RpcPool` with its budget and denied methods; they happen only for a coin that passed the free NATS checks and is about to be watched, never for the whole firehose.
- The pump.fun HTTP API sits behind `pumpGet`'s per-path backoff (`pump-http.ts:18`). When a path is resting after a 429, the lookup is skipped, counted in stats and the next source tried, not waited on.
- Every threshold (`max_dev_buy_sol`, `max_block0_sniper_share`, `max_bundle_share`) and every `on_unknown` rule lives in `config/filters.json` `launch`; the code holds no number, and a change is an edit and a restart.
- The launch door is Solana only: the trade stream and launch messages carry Solana coins only (measured). Other chains are in `docs/LATER.md`.
- `unknown` is decided by config, not code: `config/filters.json` `launch.on_unknown` is `refuse` for the `heat` and `metrics` reasons (no evidence of quality) and `pass` for `caller_buy`, `smart_buy` and `follow` (the wallet is the evidence). Every unknown is counted per fact.
- After promotion, Backfill reads the coin's first trades from RPC anyway. If the chain features disagree with the NATS ones, write `system.source_disagree` (RPC wins, `docs/PIPELINE.md` section 2), re-run the filter, and if the coin now fails, stop watching it with a note.
- Not in B3: a second live stream from RPC (needs Anchor event decoding and still misses pump-swap trades).

## Invariants
The deny list is the owner's existing `blocked_wallets` and `blocked_creators` (known bad deployers and traders); the door checks both the creator and the trigger wallet. The list is loaded only by `ctl lists load`; no code adds to it (owner decision 2026-10-19).
The Risk Gate keeps its own blocklist check: the door adds a wall, it does not replace one. The filter uses only features known at the trigger trade (no lookahead).
